# 동시성 제어 방식 분석 보고서

## 1. 동시성 문제 상황

### 1.1 발생 가능한 동시성 문제

포인트 관리 시스템에서는 다음과 같은 동시성 문제가 발생할 수 있습니다:

**문제 시나리오 예시**
```
초기 상태: 사용자 A의 포인트 = 10,000원

[Thread 1] 포인트 조회: 10,000원
[Thread 2] 포인트 조회: 10,000원
[Thread 1] 1,000원 사용 → 잔액 업데이트: 9,000원
[Thread 2] 1,000원 사용 → 잔액 업데이트: 9,000원

예상 결과: 8,000원
실제 결과: 9,000원 (데이터 손실 발생!)
```

### 1.2 Race Condition 발생 지점

- **포인트 충전**: 동시에 여러 충전 요청 시 일부 충전 금액이 손실될 수 있음
- **포인트 사용**: 동시에 여러 사용 요청 시 잔액보다 많은 금액이 사용될 수 있음
- **잔액 검증**: 사용 가능 금액 체크와 실제 차감 사이의 시간 차로 인한 문제

## 2. 동시성 제어 방식 선택

### 2.1 선택한 방식: 사용자별 ReentrantLock

`PointService`에서 **사용자별 비관적 락(Pessimistic Lock)** 방식을 적용했습니다.

### 2.2 다른 방식과의 비교

| 방식 | 장점 | 단점 | 선택 여부 |
|------|------|------|-----------|
| **synchronized 메서드** | 구현 간단 | 모든 사용자가 같은 락을 공유하여 성능 저하 | ❌ |
| **ReentrantLock (전역)** | 구현 간단 | 모든 사용자가 같은 락을 공유하여 성능 저하 | ❌ |
| **사용자별 ReentrantLock** | - 사용자별 독립적인 락<br>- 다른 사용자 요청에 영향 없음<br>- 공정성 제어 가능 | Lock 관리 코드 필요 | ✅ **채택** |
| **낙관적 락 (Optimistic Lock)** | 충돌이 적을 때 성능 우수 | - 충돌 발생 시 재시도 필요<br>- In-memory DB에 버전 관리 어려움 | ❌ |
| **Database Lock** | DB 레벨 트랜잭션 보장 | In-memory DB는 실제 DB 락 미지원 | ❌ |

### 2.3 선택 이유

1. **사용자별 격리**: 사용자 A의 포인트 작업이 사용자 B에게 영향을 주지 않음
2. **성능 최적화**: 전역 락 대비 동시 처리량이 높음
3. **공정성**: `ReentrantLock`의 공정 모드 설정 가능 (필요 시)
4. **명시적 제어**: try-finally로 확실한 락 해제 보장

## 3. 구현 상세

### 3.1 포인트 충전 (`chargePoint` 메서드)

**포인트 충전 정책**
1. 10포인트 단위로 충전 (1포인트 단위는 절삭 17p -> 10p)

**동작 순서**
1. 사용자 ID로 전용 Lock 획득
2. Lock을 획득할 때까지 대기 (다른 스레드가 해당 사용자의 작업 중이면)
3. 충전 로직 수행
4. finally 블록에서 반드시 Lock 해제

### 3.2 포인트 사용 (`usePoint` 메서드)

**포인트 사용 정책**
1. 최소 1000포인트 이상 사용 가능
2. 500포인트 단위로 사용 가능
3. 현재 보유 포인트가 5000 이상일 시 사용 가능

**검증 로직의 안전성**
- Lock 내부에서 모든 검증과 업데이트 수행
- 조회 시점과 업데이트 시점 사이에 다른 스레드가 개입 불가능
- 5000원 미만 사용 불가 조건도 원자적으로 처리됨

### 동시성 구현 시 포인트 충전과 사용 정책도 만족하는지 테스트 수행

### 3.3 조회 메서드는 Lock 미적용

**이유**: 읽기 전용 작업은 Lock 없이 수행하여 조회 성능 최적화

## 4. 동시성 테스트 결과

### 4.1 Unit 테스트 (`PointServiceConcurrencyTest`)

#### 테스트 1: 동시 충전 요청

- **시나리오**: 10개 스레드가 동시에 1,000원씩 충전

- **테스트 결과**: ✅ **통과** - 모든 충전이 정확히 반영됨

#### 테스트 2: 동시 사용 요청

- **시나리오**: 5개 스레드가 동시에 1,000원씩 사용
- **기대 결과**: 10,000 - (1,000 × 5) = 5,000원
- **테스트 결과**: ✅ **통과** - 모든 사용이 순차적으로 처리됨

#### 테스트 3: 충전과 사용 동시 처리

- **시나리오**: 충전 5회(1,000원) + 사용 3회(1,000원) 동시 실행
- **기대 결과**: 10,000 + 5,000 - 3,000 = 12,000원
- **테스트 결과**: ✅ **통과** - 충전/사용이 섞여도 정확한 계산

#### 테스트 4: 서로 다른 사용자 동시 요청

- **시나리오**: 사용자1, 사용자2가 각각 5번씩 충전 (동시 실행)
- **기대 결과**: 각 사용자 15,000원

#### 테스트 5: 최소 보유 금액 검증 (동시성)

- **시나리오**: 6,000원에서 1,000원씩 3번 동시 사용 시도

  - 나머지 6번은 잔액 부족 또는 최소 보유 금액 미달로 실패

## 5. 성능 분석

### 5.1 Lock 경합 (Lock Contention)

**긍정적 측면**
- ✅ 사용자별 독립적인 Lock으로 경합 최소화
- ✅ 사용자 A와 사용자 B는 서로 대기 없이 동시 처리 가능

**주의할 점**
- ⚠️ 동일 사용자의 요청이 많을 경우 대기 시간 증가
- ⚠️ DB 지연(200~300ms)으로 인해 Lock 보유 시간이 길어질 수 있음

### 5.2 메모리 사용량

- `ConcurrentHashMap<Long, ReentrantLock>`: 사용자 수에 비례하여 증가
- **개선 가능성**: 일정 시간 사용하지 않은 Lock 정리 메커니즘 고려

### 5.3 처리량 (Throughput)

**단일 사용자 기준**
- Lock으로 인해 순차 처리됨 (동시성 제어의 목적)
- DB 지연 시간(200~300ms)이 주요 병목

**다중 사용자 기준**
- 병렬 처리 가능 → 전역 Lock 대비 처리량 N배 향상 (N = 동시 사용자 수)

## 6. 한계 및 개선 방안

### 6.1 현재 방식의 한계

1. **Lock 메모리 누적**
   - 사용자 수가 많아질수록 `ConcurrentHashMap`의 크기 증가
   - 한 번 생성된 Lock은 제거되지 않음

2. **공정성 미보장**
   - 현재는 non-fair Lock (기본값)
   - 요청 순서대로 처리되지 않을 수 있음

3. **In-Memory DB의 한계**
   - 실제 DB였다면 트랜잭션 레벨 락, SELECT FOR UPDATE 사용 가능
   - 현재는 애플리케이션 레벨 락에 의존

### 6.2 개선 방안

#### 개선안 1: Lock 자동 정리
```java
// LoadingCache 활용 (Guava 또는 Caffeine)
private final Cache<Long, ReentrantLock> userLocks = Caffeine.newBuilder()
    .expireAfterAccess(Duration.ofMinutes(10))
    .build();
```

#### 개선안 2: 공정한 Lock
```java
private Lock getUserLock(long userId) {
    return userLocks.computeIfAbsent(userId, id -> new ReentrantLock(true)); // fair=true
}
```

#### 개선안 3: 실제 DB 사용 시 고려사항
```java
// JPA Pessimistic Lock
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT u FROM UserPoint u WHERE u.id = :id")
UserPoint findByIdWithLock(@Param("id") Long id);
```
